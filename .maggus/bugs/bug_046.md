# Bug: Multiple inconsistent task-readiness checks instead of one canonical classifier

## Summary

Three separate functions decide whether a task is "ready to run", and they disagree. The daemon pre-check uses `IsWorkable()` (no predecessor awareness), the orchestrator uses `classifyWorkable` (predecessor-aware), and the execution plan display uses `hasUnknownPredecessor` (a third, display-only variant). The gaps between them cause the "Preparing" hang (BUG-045) and allow the execution plan display to show a different ordering from what the orchestrator actually executes.

## Root Cause

| Call site | Function used | Checks predecessors? |
|---|---|---|
| `countWorkable` (`run_loop.go:154`) | `IsWorkable()` | No |
| `firstWorkableTask` (`run_loop.go:214`) | `IsWorkable()` | No |
| Orchestrator inner loop (`orchestrator_parallel.go:117`) | `classifyWorkable` | Yes — requires completedIDs map |
| Execution plan display (`status_execution.go`) | `hasUnknownPredecessor` | Partial — detects missing IDs only |

Because `countWorkable` and `firstWorkableTask` are blind to predecessors, the daemon can decide there is work available and write a "Preparing" snapshot for a task the orchestrator will immediately reject. Because the execution plan uses a third, display-only check, its ordering can differ from what the orchestrator actually runs.

## Expected Behavior

One canonical function — with predecessor context — determines whether a task is runnable. Every call site (daemon pre-check, orchestrator loop, execution plan display) uses the same function so they can never disagree.

## User Stories

### BUG-046-001: Introduce a single canonical task-readiness function and use it everywhere

**Description:** As a developer, I want one function that answers "can this task run right now?" so that the daemon pre-check, the orchestrator, and the execution plan display are always consistent.

**Acceptance Criteria:**
- [ ] A new function (e.g. `IsRunnable(completedIDs, skippedOrBlockedIDs map[string]bool) bool` on `parser.Task`, or a package-level helper) encapsulates the full check: `IsWorkable()` + predecessors satisfied (predecessor is complete, blocked, or skipped)
- [ ] `countWorkable` is updated (or replaced) to use the new function with proper predecessor context
- [ ] `firstWorkableTask` is updated to use the new function so the "Preparing" snapshot always reflects a task the orchestrator will actually run
- [ ] `classifyWorkable` in the orchestrator is updated to use the same function, eliminating the inline predecessor loop
- [ ] The execution plan builder (`status_execution.go`) derives its "unresolved" classification from the same logic rather than a separate `hasUnknownPredecessor` check
- [ ] Callers that do not yet have predecessor context (e.g. early daemon setup) pass empty maps so the function degrades gracefully to the current `IsWorkable()` behavior
- [ ] All existing orchestrator and parser tests continue to pass
- [ ] `go vet ./...` and `go test ./...` pass
