# Bug: Completed task Output tab breaks TUI layout

## Summary

Viewing the Output tab for a completed task breaks the entire TUI layout. The pane boundaries, borders, and content overlap or shift. Likely caused by the rendered content exceeding the allocated height or width, causing lipgloss to wrap or clip incorrectly.

## Steps to Reproduce

1. Open `maggus` → status view
2. Expand a feature with completed tasks
3. Navigate to a completed task (one that has run log history)
4. Switch to the Output tab
5. Observe: the TUI layout breaks — borders misaligned, content overflows

## Expected Behavior

The Output tab should render the completed task's tool history within the right pane boundaries, with scrolling for long output, without breaking the split-pane layout.

## Root Cause

Candidate causes, ranked by likelihood:

### 1. Double height/width wrapping (most likely)

`renderCompletedTaskOutput()` in `status_task_output.go:401` wraps its output with `lipgloss.NewStyle().Width(width).Height(height).Render(sb.String())`. Then `renderRightPane()` in `status_rightpane.go:83` wraps the combined `tabBar + sep + content` again with `.Width(width).Height(height).Render(full)`. The double application of `.Width()` can cause lipgloss to re-wrap already-styled lines, inserting extra line breaks. The extra lines push content beyond the allocated height, breaking the layout.

This is the same rendering approach used by `renderSnapshotInPane` for running tasks — but running task snapshots typically have fewer tool entries (they're still accumulating), so the issue is less visible.

### 2. Tool description line wrapping

`buildToolLines()` in `status_task_output.go:23-53` computes `contentWidth = width - 4` and truncates descriptions. But `styles.RightAlign()` computes padding using `lipgloss.Width()` which measures visible width. If any tool description contains characters where visible width differs from byte/rune width (emojis, CJK, tab characters from Bash commands), the padding calculation could be wrong, producing lines wider than expected.

### 3. Overhead constant mismatch

`renderCompletedTaskOutput()` uses `available = height - 9` (line 364) for the scrollable tool list. Counting the actual fixed lines: top zone = 3 (status + task + separator), bottom zone = 5 (separator + tokens + cost + duration + tools). That's 8 lines of overhead, not 9. This means one fewer tool line is rendered than the space available, leaving a gap — but this alone wouldn't break the layout.

## User Stories

### BUG-031-001: Fix Output tab rendering for completed tasks

**Description:** As a user viewing a completed task's Output tab, I want the tool history to render correctly within the right pane without breaking the TUI layout.

**Acceptance Criteria:**
- [ ] Investigate whether `renderCompletedTaskOutput` produces content that exceeds the allocated dimensions — add debug logging of `strings.Count(sb.String(), "\n")` vs `height` to confirm
- [ ] If double wrapping is the cause: remove the inner `lipgloss.NewStyle().Width(width).Height(height).Render()` call in `renderCompletedTaskOutput` and return the raw `sb.String()` — let `renderRightPane` handle the final sizing (same pattern should apply to `renderSnapshotInPane`)
- [ ] If line wrapping is the cause: ensure every tool line in `buildToolLines` is truncated to `contentWidth` as measured by `lipgloss.Width()`, not just rune count
- [ ] Fix the overhead constant: `height - 9` should be `height - 8` (3 top + 5 bottom = 8)
- [ ] Viewing a completed task with 100+ tool entries does not break the layout
- [ ] Viewing a completed task with 0 tool entries shows "No tool invocations recorded" cleanly
- [ ] Scrolling (up/down/g/G) works correctly on long completed task output
- [ ] No regression in running task Output tab rendering
