# Bug: Parallel orchestrator loops forever when worktree already exists

## Summary

When a parallel task fails during worktree creation (because a leftover worktree from a previous interrupted run already exists), the orchestrator retries the task indefinitely — the task is never excluded from `classifyWorkable`, so the outer `run` loop never terminates. Each retry also appends duplicate entries to `workerOrder`, causing the status TUI to display the same worker tasks repeating endlessly.

## Steps to Reproduce

1. Start the daemon in parallel mode with feature 040 (tasks 002, 003, 004 are parallel)
2. Interrupt the daemon mid-run (e.g., `maggus stop`)
3. Restart the daemon
4. Observe the status TUI: tasks 002, 003, 004 appear in an ever-growing repeating list

Confirmed worktrees are still registered after interruption:
```
C:/c/maggus/.maggus/worktrees/TASK-040-002  [feature/maggustask-040-002]
C:/c/maggus/.maggus/worktrees/TASK-040-003  [feature/maggustask-040-003]
C:/c/maggus/.maggus/worktrees/TASK-040-004  [feature/maggustask-040-004]
```

## Expected Behavior

When a parallel task fails (for any reason), the orchestrator should not retry it. Failed tasks should either:
- Be recorded in a skip set so `classifyWorkable` excludes them on subsequent iterations, OR
- Cause the orchestrator loop to break when no tasks made progress

Additionally, the status TUI should not show duplicate worker entries even if retries occur.

## Root Cause

Two bugs compose to produce the symptom:

### Bug 1: No termination condition for failed tasks (primary)

`parallelOrchestrator.run()` in `src/cmd/run_parallel.go:136–181` loops calling `classifyWorkable` → `runParallelBatch` indefinitely. The only exit conditions are:
- `classifyWorkable` returns empty (no workable tasks)
- `StopReasonInterrupted` is returned

But when a task fails — specifically at `runSingleTask` line 285–287:
```go
if err := gitworktree.CreateWorktree(o.repoDir, worktreePath, taskBranch); err != nil {
    o.markWorkerFailed(task.ID, wsw)
    return o.failTask(&result, workerLogger, task, ...)
}
```

`failTask` adds the task to `result.failed` but does **not** add it to `o.completedIDs`. `classifyWorkable` only skips tasks where `t.IsComplete()` or `t.IsBlocked()` returns true (from the parsed file), or where `o.predecessorsComplete` fails. A failed task satisfies none of these conditions, so it is returned again on the next iteration — indefinitely.

The concrete trigger: `gitworktree.CreateWorktree` (`src/internal/gitworktree/gitworktree.go:20`) calls `git worktree add path branch`, which fails with "already exists" when the worktree directory is already registered. `CreateBranchFrom` is idempotent (returns nil if branch exists), so branch creation never fails — but worktree creation fails on every retry.

### Bug 2: `registerWorker` appends duplicates (secondary — produces the visible TUI symptom)

`registerWorker` in `src/cmd/run_parallel_tui.go:187` always appends to `o.workerOrder`:
```go
o.workerOrder = append(o.workerOrder, taskID)
```

There is no deduplication check. When the same batch is retried, the same task IDs are appended again. `buildWorkerEntries` iterates the full `workerOrder` slice, so `WriteWorkersIndex` writes an ever-growing list with repeated entries. The status TUI reads this index on each poll tick and renders each entry, producing the visual "endless loop" the user sees.

## User Stories

### BUG-028-001: Add failed-task skip set to break the infinite retry loop

**Description:** As a user, I want the parallel orchestrator to stop retrying tasks that have failed so the daemon does not loop endlessly after a failure.

**Acceptance Criteria:**
- [x] `parallelOrchestrator` gains a `failedIDs map[string]bool` field (alongside `completedIDs`)
- [x] When `runSingleTask` returns a failed result (any failure path: branch, worktree, agent, commit, or merge error), the orchestrator records the task ID in `failedIDs` before the outer `run` loop iterates again
- [x] `classifyWorkable` skips tasks whose ID is in `failedIDs` (in addition to the existing `IsComplete` / `IsBlocked` checks)
- [x] After the fix, restarting the daemon with existing worktrees does not produce an infinite loop — the daemon logs the failures and exits cleanly
- [x] `go vet ./...` and `go test ./...` pass
- [x] No regression in normal parallel task completion flow

### BUG-028-002: Deduplicate `registerWorker` to prevent growing worker index

**Description:** As a user, I want the worker status panel in the TUI to never show duplicate task entries, even if the orchestrator retries a task.

**Acceptance Criteria:**
- [x] `registerWorker` checks `o.workerOrder` (or a lookup map derived from `workerStatuses`) before appending; if the task ID is already registered, the append is skipped
- [x] `buildWorkerEntries` never produces duplicate rows for the same task ID
- [x] After the fix, the status TUI worker list shows each task at most once regardless of retry count
- [x] `go vet ./...` and `go test ./...` pass
- [x] No regression in normal parallel task completion flow

### BUG-028-003: Make `CreateWorktree` idempotent for already-registered worktrees

**Description:** As a developer, I want `gitworktree.CreateWorktree` to succeed (or be skippable) when the worktree path is already registered, so interrupted parallel runs can resume cleanly.

**Acceptance Criteria:**
- [ ] `CreateWorktree` in `src/internal/gitworktree/gitworktree.go` checks if the given path is already a registered worktree (via `ListWorktrees` or `git worktree list --porcelain`) before calling `git worktree add`
- [ ] If the path is already registered and points to the expected branch, the function returns `nil` (idempotent success)
- [ ] If the path is registered but on a different branch, the function returns a descriptive error
- [ ] `go vet ./...` and `go test ./...` pass
- [ ] Existing `CreateWorktree` tests remain green; a new test covers the already-registered case
